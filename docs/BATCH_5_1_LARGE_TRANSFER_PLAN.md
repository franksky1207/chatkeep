# ChatKeep v1.1.0｜第 5-1 批：大型選取對話傳輸與容量架構修正（Codex）

狀態：**Codex 技術實作及合成測試完成，待驗收，未部署**。已知第 5 批基準 commit：`73bd2ecda3c8f8ddf91f432d890421357b576b82`；執行時以遠端開發分支最新版為準。本批加入於第 5 與第 6 批之間，沿用 `feat/local-json-extractor`、Draft PR #3。第 8 批才做真實備份、手機／桌機、Word 與 Render Free 實機驗收。

## 一、確認的瓶頸及必守原則

現行 `POST /api/convert-json` 單次請求上限 2,000,000 bytes，儘管共用 Word 核心已具備單檔優先、分卷及 ZIP，超長原始官方對話物件（特別是龐大 mapping、metadata、非當前分支）仍易於傳輸入口遭拒絕。不能直接調高到數十／數百 MB，亦不能把整份 440 MB 備份傳到 Render。

- 只有使用者明確選取的對話才允許離開本機。未選取的對話、非必要 metadata 與整包備份絕不可被傳送。
- 原始擷取 JSON 下載保持原樣，分段傳輸另用**明確標記的衍生表示**，不可冒充保留全部官方 JSON。
- 在瀏覽器本機以已選對話物件為起點，完成 `current_node`／parent 鏈驗證、循環／重號／可見與略過分類，再建立最小化、依序排列的有效輸出訊息資料；**不得僅用 regex 或 mapping 插入順序簡化**。必須區分「本機可重建的輸出序列」與「經伺服器驗證的完整性」，不可讓前端自行聲稱來源逐字完整。
- 一般可安全通過目前 API 的對話，仍走既有 `/api/convert-json`，保留單 DOCX 優先。
- 大型對話，採用**無伺服器私人持久化、可驗證、每批有界、完整訊息邊界**的協定。每批上限可仍為 2 MB，不能裁斷單則訊息，也不得以壓縮炸彈／Zip64 繞過限制。
- 不能讓後端將一批合法資料錯誤當成完整官方對話，也不能把不屬於同一選取對話的批次錯誤合併。
- **跨多次 API 呼叫無法憑空產生一個合併 DOCX**：若不建立安全、有界的跨請求狀態，採用「每批各自 DOCX、最終由瀏覽器驗證並封裝 ZIP」的明確替代。不能欺騙使用者已產出單一 Word；可在有限單次輸入時仍維持單檔。
- Render 免費方案 45 秒 CPU／wall、記憶體／速率／並行、429 與上傳逾時均須重新盤點。切批應確實能降低一次運算負擔，不能因每批重建整段對話或重複擷取放大負載。
- 當一則訊息**自身**超出單次傳輸／單卷資源界線，不許靜默切訊息；請明確標出 `MESSAGE_TOO_LARGE`／`CHUNK_TOO_LARGE` 等具體原因；特殊超長訊息的處理需要另經有界安全設計，不得宣稱本批可以處理一切尺寸。

## 二、架構比較與決策

Codex 必須先在文件列出至少兩種可行選項的記憶體、隱私、錯誤恢復與安全成本：
A. 瀏覽器衍生有效訊息序列，分段呼叫無狀態後端，每段輸出單卷 Word，前端 ZIP 組裝；
B. 安全的暫時性串流／會話式服務端組卷（需 session TTL、配額、認證 token、清理與併發限制）。

**免費 Render 優先 A**；只有有測試證據與明確清除機制才考慮 B。不得保留所有 batch 私人內容於全域 Python dict／無界磁碟。具體 API 名稱／schema 由 Codex 根據既有 `official_json.py`、`conversation_export.py`、`json_api.py` 決定，必須版本化且可供第 6 批直接承接。

## 三、實作範圍與完整性證據

1. 建立共用的、獨立測試可驗證的有效輸出序列封包格式（如 `schema_version`、`conversation_key`、`source`、`part_index`、`part_total`、`first_message`、`last_message`、`message_count`、`sequence_sha256`）；不要依照檔名或標題驗證批次歸屬。對來源 id、訊息 role／text、canonical hash 提供明確規範及 test vectors。
2. 正規化時必須先對**單一已選官方對話**做結構／目前分支／隱藏／工具／非文字訊息檢查；不安全、未完成或未知可見內容時 fail closed。若瀏覽器端無法完成驗證，應明確拒絕這條快速傳輸路徑，避免悄然遺漏。
3. 依**完整訊息**切批，連續索引、原始順序、批次 SHA-256、總序列 SHA-256 與計數皆可核對；防重複、防缺漏、防交換順序、防混入其他選取對話。伺服器只處理當次 chunk，保持私密無狀態，不信任使用者傳送的 `complete=true` 旗標。
4. 轉換核心沿用 `WordVolume`／`conversation_export`／`rich_word`，不建立第二套排版器；每批文件可獨立開啟。若單批仍達到 Word 結構上限，可在批內依第 5 批原則分卷；使用全域訊息序號，最終卷號與檔名不衝突。
5. 對於分段結果應產生驗證清單（可不含私密本文）供第 6 批前端檢查完整序列，所有分卷完全成功後才准產出最終 ZIP；支援明確取消、失敗可重試指定批，且不把不完整 ZIP 當成功。前端完整整合 UI／下載／跨站 CORS 仍歸第 6 批。
6. 如需新增瀏覽器本機準備模組，獨立於第 2 批原始 `Blob.slice` 索引／提取流程，保持 worker 與記憶體有界；原始 JSON 下載功能不得變更。使用有效分支資料是衍生轉換材料，不可宣稱原樣保存所有 mapping。
7. 盡可能沿用現有 SLOTS／RateLimit、來源驗證及隱私政策；新增批次頻率、總量與總卷數政策必須與 10 次／分鐘速率協調（例如有節制的順序處理和明確等待／429 重試，不得提高匿名 API 到無限制）。
8. 更新 API 契約、失敗碼、網路限制、Render Free 評估、舊分享連結 v1 與 v2 相容性；不增加無界 memory、tmp、日志、跨來源代理或部署設定。

## 四、驗收基準（合成資料）

- 小型官方 JSON → 既有單 DOCX 原行為一致；公開分享連結 v1／v2 不退化。
- 大於 2 MB、但由大量映射／metadata 造成冗餘的單一已選對話 → 不上傳無關 metadata／非當前分支，分段後能正確轉成 DOCX／ZIP。
- 真正超長有效文字 → 多批、完整訊息邊界、全域順序、無漏／重／錯卷；最後 ZIP 各卷 bookmark、CRC 和 SHA-256 與來源衍生序列一致。
- 刻意交換、遺漏、重複、損壞或混入其他對話的 batch → 拒絕／不宣告完成；同批重試必須冪等，不能重複進 ZIP。
- 單則訊息太大、批次過多、總量／ZIP 太大、無法完成來源分支判定、不支援多媒體、429、逾時、程序中止、客戶端取消 → 明確報錯、安全回收、不回傳貌似完整的結果。
- 獨立有限資源的合成測試（傳輸位元組數、CPU 秒、RSS 峰值、請求數、客戶端記憶體），實際 Render Free、Safari／桌機與真實備份留第 8 批。
- 只執行本批相關測試與必要回歸；不得自動開始第 6 批。
